# 我的系统如何做到不交叉

## 背景

"不交叉"是[解决 agent 任务冲突的三个策略](./解决agent任务冲突问题的三个策略.md)中成本最低、效果最好的一个——如果两个 agent 的变更集在依赖图上没有交集，它们天然不会冲突，根本不需要协调。

问题是：ProjectPilot 现在能做到哪些事情来帮助"不交叉"？有哪些潜力还没发挥？

以下按**投入产出比从高到低**排列。

---

## 现在已经能做的

### 1. Flow 树按模块划分 Section

**投入：零（已有功能）**

Flow 树的 Section 可以按代码模块划分——前端 Section、后端 Section、数据库 Section。不同 Section 的任务天然隔离度更高，同一 Section 内的任务可能有依赖。

现在完全靠人的判断来决定如何划分和哪些任务可以并行。这已经是最基础的"不交叉"工具，只是没有系统辅助。

### 2. Prompt 限定 Agent 作用域

**投入：低（改 prompt）**

在 prompt 中约束 agent 的工作范围："你只负责 `/src/api/` 下的文件，不要碰其他目录。"

ProjectPilot 已经有 Agent 模型（`agentId`、`capabilities`），也有 `buildAgentToolArgs` 和 `buildAgentPermissionArgs`。可以进一步利用 Agent 的配置，在 prompt 中注入作用域限制。

**局限**：这是软约束。AI 可能越界——它需要读其他目录的代码来理解上下文，或者判断某个改动需要同时修改其他地方。Claude Code 的 `--allowedTools` / `--disallowedTools` 是按工具类型控制的（Bash、Edit、Read...），不是按路径控制的，所以工具级别做不到路径隔离。

不过，也可以做更细粒度的路径约束——比如利用 Agent 的 capabilities 配置一个 `scope` 字段（允许的目录列表），在 prompt 构建时注入明确的路径限制指令。虽然仍是软约束，但比泛泛的"只负责这个模块"更具体、AI 更容易遵守。

---

## 有潜力做到的

### 3. Planning 阶段声明 affected_files（最值得先做）

**投入：低（改 prompt + 比对逻辑）**

让 AI 在规划阶段多输出一个字段，声明这个任务预计会修改哪些文件：

```json
{
  "steps": [...],
  "affected_files": ["src/api/user.ts", "src/types/user.ts"],
  "affected_modules": ["api", "types"]
}
```

**工作流程**：

1. 用户在 Flow 树里拆分了兄弟任务 A、B、C
2. 每个任务各自跑完 Understanding → Planning
3. Planning 完成后，系统拿所有兄弟任务的 `affected_files` 做交集
4. 交集非空 → UI 上标记警告："Task A 和 Task B 都要改 `user.ts`"
5. 用户自己决定：串行做，还是接受冲突之后再处理

**本质**：让 AI 在规划阶段预报自己要动哪些文件，系统自动帮用户比对兄弟任务之间有没有重叠。判断发生在 Planning 完成后、Executing 开始前。做判断的是系统代码，不是 AI。

**局限**：这是 AI 的预测，不保证准确。AI 说要改 3 个文件，实际执行可能改 5 个。所以是软判断，提醒用，不是保证。但代价几乎为零——只需要改 prompt 和加一个比对逻辑。

### 4. 基于 import graph 的依赖分析

**投入：高（需要静态分析模块）**

项目启动时扫描一次 import 关系，构建模块依赖图。用户在 Flow 树拆任务时，系统根据任务描述匹配到可能涉及的模块，自动检查两个任务的模块是否在依赖图上有交集。

这比 affected_files 更早——在 Planning 之前、甚至在 Understanding 阶段就能做。但实现成本高，需要一个静态分析模块（对于 TypeScript 项目，可以基于 `ts-morph` 或 `madge` 等工具）。

### 5. Worktree + 路径白名单

**投入：中（worktree 管理 + 权限设置）**

给每个 task 创建 worktree 的同时，用文件系统权限或 git 配置限制 agent 只能改特定目录。这是硬约束。

**局限**：粒度粗。agent 可能需要**读**（不是写）其他模块的代码来理解上下文，如果连读都限制了，agent 的工作质量会下降。而且实践中 Claude Code 经常不按预期切 worktree、切分支，这块的收益取决于能否让 Claude 可靠执行。

---

## 优先级总结

| 方案 | 投入 | 效果 | 建议 |
|---|---|---|---|
| Section 按模块划分 | 零（已有） | 靠人判断，有用但不精确 | 继续用 |
| Prompt 限定作用域 | 低（改 prompt） | 软约束，AI 可能越界 | 可以先做 |
| **Plan 声明 affected_files** | **低** | **软判断，能提前预警** | **最值得先做** |
| Import graph 分析 | 高 | 最精确的预判 | 后期再考虑 |
| 路径白名单 | 中 | 硬约束但粗糙 | 看需求 |

**推荐的第一步**：Plan 声明 affected_files + 兄弟任务交叉检测。改动小，能让用户在执行前就看到哪些任务可能冲突，然后自己决定怎么处理。
