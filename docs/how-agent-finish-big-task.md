# 如何让 Agent 把一整件大事做完

> 创建日期：2026-04-08

---

## 问题

让 agent 一次做完一个大功能或大重构，现在总是做不好。

不是因为缺一个功能，而是因为大任务天然超出了单次 agent 执行的能力边界。大事和小事的区别不在于"量多"，而在于**决策链长**。决策链一长，三个问题就出来了：

1. **迷路**：agent 做到第 15 步时已经忘了第 3 步做了什么决定。人会"抬头看路"，agent 不会。
2. **不会止损**：碰到困难时一直往前冲，不会退一步重新评估。
3. **不确定性累积**：每步都有误差，20 步下来误差叠加到无法收拾——没有纠偏机制。

结论：**不是让 agent "一次做完"，而是让系统把大事拆成 agent 能可靠完成的单元，然后串起来。**

问题变成了：用什么方式拆、怎么串？

---

## 两条路线

### 路线 A：结构驱动（图/树 + 索引）

智能在**结构**里。Agent 是执行者，从结构中取任务、按结构定的顺序做、往结构里写结果。

类比：**一个人 + 一块非常详细的看板**。看板上写清了每件事、依赖关系、验收标准。按看板做，做完一个勾一个。

### 路线 B：分职能 Agent（planner / coder / reviewer / ...）

智能在 **agent 群体**里。结构是 agent 之间涌现出来的副产品。

类比：**一个小团队**。架构师出方案，程序员写码，测试员验证，互相传话协调。

---

## 逐维度对比

| 维度 | 结构驱动（图/树） | 分职能 Agent |
|------|-----------------|-------------|
| **状态可见性** | 高——图上一看就知道做到哪、卡在哪 | 低——状态分散在各 agent 的上下文里 |
| **可恢复性** | 强——崩了重启，从图的状态继续 | 弱——agent 挂了，上下文就没了 |
| **人类可干预** | 容易——改图就行，删节点、加依赖、调优先级 | 难——得理解 agent 之间的对话链路 |
| **分解质量依赖** | 极高——图拆错了后面全错 | 较低——agent 群体有一定自纠偏能力 |
| **应对意外** | 弱——图是静态的，做到一半发现前提错了，图不会自己更新 | 强——agent 之间能讨论、能临时调整 |
| **token 效率** | 高——每个 agent 只看自己那个节点 + 必要上下文 | 低——每个 agent 都需要全局上下文，大量重复 |
| **协调成本** | 几乎为零——结构本身就是协调 | 很高——通信、等待、误解都是成本 |
| **并行能力** | 天然支持——图上无依赖的节点同时执行 | 受限于角色流水线 |
| **适合的任务类型** | 可预先分解的、结构清晰的 | 探索性的、需要创意或多角度评审的 |

### 各自的致命伤

**结构驱动的致命伤：图是死的。** 执行到第 5 个节点时发现第 2 个节点的方案得改——图不会自动更新。要么让 agent 改图（容易失控），要么暂停等人改（打断自动化），要么硬做下去（做废活）。

**分职能 Agent 的致命伤：通信是贵的、有损的。** Planner 传方案给 Coder 时，压缩了信息、丢失了隐含假设。Coder 基于不完整的信息做出不同解读。跟人类团队的"传话失真"一模一样，但人有面对面沟通来弥补，agent 没有。

---

## 融合方案

两条路线不是对立的。与其预设"你是 planner""你是 coder"这种固定身份，不如**根据 agent 在这次做的事来定义它的角色**。同一个 agent，接到"制定计划"的指令时它就是 planner，接到"实现这个函数"的指令时它就是 coder。角色是临时的，由当前任务上下文决定。

这样结构和 agent 就融合了——**结构是"做什么"的描述，agent 是"做"的动作，agent 在结构中的位置决定了它此刻的角色。**

### 具体模型

```
一次会话
│
├─ 阶段 1：制定大 Plan
│  agent 角色 = planner
│  产出 = 一张 ≤7 个任务的图（带依赖关系）
│
└─ 阶段 2：逐个执行任务
   │
   ├─ 任务 1
   │  ├─ plan（agent 角色 = 该任务的 planner）
   │  ├─ execute（agent 角色 = 该任务的 doer）
   │  └─ verify（agent 角色 = 该任务的 checker）
   │
   ├─ 任务 2
   │  ├─ plan
   │  ├─ execute
   │  └─ verify
   │
   └─ ...最多 7 个
```

### 关键设计点

**"7 个以内"**：匹配模型的认知带宽。同时追踪超过 7 件事就开始丢东西。如果一个大功能拆出来超过 7 个任务，需要再加一层——先分成 2-3 个阶段，每个阶段内再 ≤7 个任务。递归结构，每一层都控制在认知带宽内。

**plan → execute → verify 是最小完整循环**：少任何一步都会出问题。没 plan 则方向不对，没 execute 则不落地，没 verify 则错误悄悄传递到下一个任务。三步的 agent "角色"不同，不是因为需要不同的模型，而是因为需要不同的提示语境。

**上下文按需注入**：每个节点的 agent 只看到自己的 goal + 依赖节点的 result。不需要看整张图。控制 token 消耗。

**图是活的但改图有门槛**：agent 执行节点时如果发现计划需要调整，不直接改图，而是标记"需要重规划"的信号，由人或 planner 模式的 agent 来决定怎么改。小改自动生效，大改暂停等人确认。

### 核心数据结构

```typescript
interface BigTask {
  goal: string;
  graph: TaskNode[];     // ≤7 个节点
  edges: Dependency[];   // 节点之间的依赖
  status: 'planning' | 'executing' | 'done' | 'needs-replan';
}

interface TaskNode {
  id: string;
  goal: string;
  dependsOn: string[];
  status: 'pending' | 'planned' | 'executing' | 'verifying' | 'done' | 'failed';
  plan?: Plan;
  result?: Result;
  verification?: Check;
  context: string;       // 从依赖节点继承来的上下文
}
```

### 执行引擎逻辑

```
1. agent（planner 模式）生成 BigTask.graph
2. 拓扑排序，找出当前可执行的节点（所有依赖已 done）
3. 对每个可执行节点：
   a. 注入该节点的 goal + 依赖节点的 result 作为上下文
   b. agent（plan 模式）→ 输出 plan
   c. agent（execute 模式）→ 执行 plan
   d. agent（verify 模式）→ 检查结果
   e. 通过 → 标记 done，存 result
      失败 → 重试 or 标记 failed，通知上层
4. 所有节点 done → 大任务完成
   某节点 failed 且无法自修复 → 触发 replan
```

## 与传统工作流（n8n / Dify）的区别

表面上很像 n8n——节点、依赖、按顺序执行。但本质不同：

| | n8n 式工作流 | 本方案 |
|---|---|---|
| **图的来源** | 人预先画好 | agent 根据目标现场生成 |
| **图的生命周期** | 静态，重复使用 | 一次性的，为这个具体任务而生 |
| **图能不能变** | 不能（或只能走预定义分支） | 能——执行中发现问题可以 replan |
| **节点之间传什么** | 数据（确定性的 JSON） | 上下文 + 理解（agent 的认知结论） |
| **节点的行为** | 确定性代码 / 固定 prompt | agent 根据当前上下文自主决定 |
| **失败时怎么办** | 重试同样的操作 | agent 诊断原因，可能改策略甚至改图 |

一句话：**n8n 的节点是函数调用，本方案的节点是委托给 agent 的一个目标。**

n8n 处理的是**确定性流程**——"每次来一个 PR，做同样的事"。
本方案处理的是**不确定性任务**——"重构这个模块"，在做之前没人知道具体要走哪些步骤。

更准确的定位：**一个 agent 在运行时为自己搭脚手架，沿着脚手架干活，必要时拆改脚手架。** n8n 的脚手架是人搭好的钢结构，固定不动。这里的脚手架是 agent 临时搭的、可拆卸、按需调整——但始终是有脚手架的，不是在空中飞。

## 竞品 / 参考项目分析

精确匹配上述完整模型的项目**不存在**。现有项目各自实现了其中的一部分：

### LangGraph Plan-and-Execute

最接近"plan → 逐步执行 → 验证"循环。

- Planner 生成计划 → Executor 逐步执行 → 条件判断是否 replan
- 计划是 agent 运行时生成的，支持 replan
- 2026 年初 PyPI 下载量约 3800 万次，企业采用率高

**像的地方**：plan-execute-replan 状态机；显式计划数据结构。
**不像的地方**：计划是**线性列表**，不是图，没有依赖关系、不能并行；没有嵌套的 plan-execute-verify 子循环；通用框架，不专门面向编程。

**参考价值**：plan-execute-replan 的状态机设计可直接借鉴。需要把线性列表升级到 DAG + 嵌套。

### STRUCTUREDAGENT（AND/OR 树，NeurIPS 2025 Workshop）

学术界最接近"用树结构做动态规划"的工作。

- AND 节点 = 所有子任务都要完成；OR 节点 = 多个策略选一个能用的
- 动态生成和修改，不是预先画好
- 失败时结构化回退：这条路不通，换另一条 OR 分支
- WebArena 上 0.526 成功率，比 AgentOccam 高 13%

**像的地方**：用树表达任务结构；运行时生成+修改；结构化的失败回退。
**不像的地方**：面向 Web 浏览任务，不是编程；树比图简单——没有任意依赖关系；只有一个 agent 沿树走，没有子任务内 plan-execute-verify 循环。

**参考价值**：AND/OR 的区分很有价值——大任务中确实有"都要做"和"选一个做"两种关系。

### OpenHands（原 OpenDevin，开源，SWE-Bench 72%）

开源编程 agent 中做得最好的之一。

- 有显式 plan（checkbox list），agent 边做边勾
- Event-sourced 架构——所有动作都记录，可回放、可恢复
- 支持 sub-agent 委托

**像的地方**：显式的 plan；event-sourced 状态管理。
**不像的地方**：plan 是简单的 checkbox 列表，不是图；没有子任务 plan-execute-verify 循环；没有 replan 机制；更偏"一个 agent 一条龙做完"。

**参考价值**：event-sourced 的状态管理值得借鉴。编程场景的具体挑战处理可以参考。

### Devin（商业产品，不开源）

- 每个任务在隔离环境（云 VM）中执行
- 完整 session replay——可以看到 agent 每一步做了什么
- 读代码、写代码、跑测试、开 PR 完整闭环

**像的地方**：隔离执行；完整可回放。
**不像的地方**：黑盒，看不到内部任务分解逻辑；似乎是一个 agent 从头做到尾，不是显式拆图。

**参考价值**：产品形态参考——怎么把 agent 做大事的过程展示给用户。

### Claude Code 子 Agent 架构

跟"同一个 agent 根据做的事定义角色"最像。

- 主 agent 按需发起子任务，选模型 + 给指令
- 子 agent 拿到干净上下文 + 明确指令，不是整个对话历史
- agent 之间通过文件系统通信（JSON mailbox）

**像的地方**：角色按需分配，不预设固定身份；子 agent 上下文隔离。
**不像的地方**：没有显式任务图——主 agent 在脑子里追踪；子 agent 是一次性的，没有自己的循环。

**参考价值**：最直接的参考。证明了"按当前任务定义角色"比"预设固定角色"更实用。

### 竞品总结

没有人做到完整模型：**图结构（不是列表）+ 运行时生成 + 可变 + 嵌套的 plan-execute-verify + 面向编程大任务**。

现有项目要么有图但不面向编程（STRUCTUREDAGENT），要么面向编程但没有图（OpenHands、Devin），要么有框架但只支持线性计划（LangGraph plan-execute）。

如果要做，最值得借鉴的组合：**LangGraph 的 plan-execute-replan 状态机** + **STRUCTUREDAGENT 的 AND/OR 结构** + **OpenHands 的 event-sourced 状态管理** + **Claude Code 的按需定义角色**。
