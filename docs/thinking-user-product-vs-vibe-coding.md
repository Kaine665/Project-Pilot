# 用户可用产品与个人「vibe coding」产品：一点思考

## 1. 现象

生成式 AI 与辅助开发工具把「做出一个**看上去**不错的软件」的门槛拉得很低：界面能看、功能能演示、甚至能跑在本地或云上。于是容易出现一种错觉：**能开发 ≈ 能交付给用户**。

一旦对象从「自己」换成「用户」，复杂度会陡然上升。本文想区分两条路：面向**用户可用**的产品，与主要服务于作者当下心流与审美的**个人 vibe coding** 产物。后者未必不好，但和前者不是同一种东西。

## 2. 真正的坑往往不在服务器

部署、域名、服务器、CI——这些当然麻烦，但多数是**可检索的工程题**：有路径、有文档、有社区经验。

更难的是另一类问题：**在时间与版本面前，产品是否仍然成立**。

- **数据**：多次版本更新之后，用户的数据是否还能被正确读取、迁移、合并？是否会静默损坏或丢失？
- **稳定**：在真实使用强度、异常操作、环境差异下，是否仍能**可预期地**工作，而不是「我机器上好好的」？
- **变更纪律**：每一个功能、每一次改动是否经过**精打细算**——是否清楚为谁服务、与现有模型是否一致、是否值得承担维护与迁移成本？而不是「今天有兴致就加一个」。

若这三条长期失守，软件就很难**真正**给用户用：不是不能安装，而是不敢依赖。

## 3. 清晰的设计意图是「用户产品」的隐形门槛

用户型产品依赖一整套**可追溯的设计意图**：

| 层面 | 对用户为何重要 |
|------|----------------|
| **需求与范围** | 用户知道产品解决什么、不解决什么；团队（或未来的你）知道这一版承诺了什么。 |
| **概念模型（领域与数据）** | 数据如何组织、对象如何命名与关联，直接决定**迁移、兼容与扩展**是否可行。 |
| **架构与契约** | 模块边界与接口稳定，版本迭代时才知道**该动哪里、不该动哪里**。 |
| **体验与界面** | 任务能否完成、误操作是否有出路，决定用户是否**愿意持续使用**。 |

个人 vibe coding 时，大量信息可以留在作者脑中：快捷键、目录结构、未写下来的规则、临时约定。换成用户产品，这些**必须外化**为文档、模型与契约，否则每一次「小改动」都可能变成对用户数据的赌博。

因此：**不是「有界面」就等于「有设计」；没有贯穿各层的意图，软件无法对用户负责。**

## 4. 两条路的合理关系

- **个人 vibe 产品**的价值在于快、真、贴己，可以大胆实验、可以承担「只有作者懂」的成本。
- **用户可用产品**的价值在于可信、可延续，必须把**数据寿命、稳定边界、变更理由**当作一等公民。

二者可以同源（从个人工具长出来），但**升格为用户产品时**，需要主动补上的不是更多功能，而是：**迁移策略、错误与降级、范围纪律，以及从需求到界面的一条清晰推理链**。

## 5. 收束

AI 很强，能让更多人越过「从 0 到演示」的墙；**用户**所代表的，是时间与责任：**版本、数据、稳定、意图**——这些才是把「能跑的软件」和「能给别人用的软件」分开的沟。
