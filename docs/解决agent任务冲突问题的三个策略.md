# 解决 Agent 任务冲突问题的三个策略

## 背景

ProjectPilot 允许多个 AI agent 并行执行编程任务，每个 task 对应一个独立的 Claude 进程。当多个 agent 同时修改同一个代码仓库时，代码仓库就是那个**共享状态**——不管用什么工具、什么进程模型、什么通信机制，只要两个 agent 的改动在依赖图上有交集，就会互相影响。

这不是工具层面的问题，也不是靠 worktree 或文件锁能根本解决的。Worktree 只是延迟了冲突（推迟到 merge 时），文件锁对黑箱的 Claude 进程不可用。

经过分析，应对这个问题的策略只有三个，它们是问题本身的解法，与具体技术无关。

## 策略一：别交叉

> 拆任务时沿模块边界切，让各 agent 的变更集不相交。

如果两个 agent 的改动涉及的文件、以及这些文件的上下游依赖，完全没有交集——它们天然不会冲突，合并后代码也不会出错。

**关键在任务分解的质量。** 拆分的人（人类用户）需要判断：这两个子任务能不能独立做？如果切在了模块边界上，agent 们天然不需要协调。如果切得不好（比如把"改用户表结构"和"改用户 API"拆成两个并行任务），冲突是必然的。

这是成本最低、效果最好的策略——问题在源头就被消除了。

详见：[我的系统如何做到不交叉](./我的系统如何做到不交叉.md)

## 策略二：别并行

> 有依赖的任务排队串行做。

如果两个任务确实有依赖（改同一个文件、共享接口、隐式耦合），最安全的做法就是不并行——先做 A，A 完成后再做 B。B 启动时能看到 A 的改动，自然不会冲突。

在 ProjectPilot 中，这意味着：
- 用户在 Flow 树中控制任务的执行顺序
- 不要同时点击多个有依赖的任务的"开始"
- 利用已完成任务的 TaskResult（summary、files_changed）注入后续任务的 prompt，让后续 agent 知道前面做了什么

这个策略的代价是**速度**——串行比并行慢。但对于有依赖的任务，这是唯一能保证不出问题的方式。

## 策略三：冲突了再解决

> 乐观并发，合并时处理冲突。

接受冲突是常态，让 agent 们各自工作，合并时再处理。这跟人类团队的工作方式一样——几个程序员并行开发，merge 时发现冲突，code review 时发现语义问题，CI 跑挂了才知道接口不兼容。

在 ProjectPilot 中，这意味着：
- 每个 task 在独立的 git 分支上工作
- 完成后合并回主分支，处理 git 冲突
- 合并后跑 CI / 类型检查来兜底（这是真正能发现语义冲突的硬检测）
- 发现问题后，启动新的 task 来修复

这个策略的代价是**返工**——冲突可能导致额外的修复工作。但对于无法预判依赖关系的情况，这是最务实的选择。

## 三个策略的关系

它们不是互斥的，而是分层防御：

```
策略一（别交叉）→ 在任务分解时消除大部分冲突
        ↓ 漏网之鱼
策略二（别并行）→ 对已知有依赖的任务强制串行
        ↓ 还是漏了
策略三（冲突了再解决）→ 兜底，合并后处理残余冲突
```

投入的优先级也应该按这个顺序——先把任务拆好（成本最低），再管控执行顺序，最后准备好冲突解决流程。
