# 标准软件开发流程（检查清单与产出物）

> **多仓库共用**：若使用独立方法论包（可发布到 GitHub 供 Raw 链接引用），见同目录 **[`methodology-package-reference.md`](./methodology-package-reference.md)**。

可重复的流程：**每一步做什么事**、**行业里通常叫什么产出物**。产出物名称可与各公司/教材略有出入，但**类型**是业内常见的。

---

## 阶段 0：立项与范围（对应「需求 + 本版边界」）

**常见任务**

- 识别干系人与主要用户
- 写清问题陈述与目标（非愿景口号）
- 列出本版本范围：必做 / 不做
- 定义验收标准（可测试、可观察）

**常见产出物**

- **问题陈述 / 项目简报**（Problem / Project brief）
- **范围说明**（Scope statement）或 **MoSCoW**（Must / Should / Could / Won’t）
- **用户故事** + **验收标准**（Acceptance criteria），或 **用例**（Use case）简述
- **成功度量**（若有）：1～3 个可量化或可归因的指标

---

## 阶段 1：领域与数据（概念模型）

**常见任务**

- 统一术语（**通用语言 / 词汇表**）
- 列出实体、关系、基数
- 标生命周期与状态（谁创建、谁结束、允许哪些变迁）
- 标「单一事实来源」：每种信息主数据在哪

**常见产出物**

- **领域模型图**（UML 类图、简版 ER、或纯文字关系表均可）
- **数据字典 / 词汇表**（Glossary）
- **状态图**（对核心对象）
- （若上关系库）**概念 ER 图** → 再进入逻辑/物理模式（这是教材里数据库设计那套）

---

## 阶段 2：架构与契约（分解 + 接口）

**常见任务**

- 划分子系统/进程/服务边界
- 定义对外接口（同步 API、消息、文件交换）
- 记录关键取舍（为何这样切）

**常见产出物**

- **C4** 里 Context / Container 级图，或等价的**系统上下文图** + **容器图**
- **接口说明**：OpenAPI/Swagger、RPC 定义，或**事件模式**（JSON Schema 等）
- **架构决策记录（ADR）**：重要技术选择各 1 页
- **依赖关系说明**（谁调用谁、数据流向）

---

## 阶段 3：体验与界面（表现层 / 任务流）

**常见任务**

- 把阶段 0 的用户路径映射到界面
- 定义关键页面/视图与导航
- 规定空态、加载、错误、权限等分支（至少主路径相关部分）

**常见产出物**

- **用户流程图**（User flow）或 **任务分析**
- **线框图 / 低保真原型**（Wireframe）
- **界面清单**（每个屏幕目的 + 主要操作）
- （可选）**设计系统 / UI 规范**（有团队或长期产品时常做）

---

## 阶段 4：质量、发布与运维（让软件「稳定可用」）

**常见任务**

- 测试策略：测什么、谁测、自动化到哪一步
- 可观测性：日志、指标、关键告警（按规模裁剪）
- 发布与回滚、配置与环境
- 数据迁移/兼容策略（若有存量数据）

**常见产出物**

- **测试计划** + **测试用例**（或等价清单）
- **非功能需求（NFR）**：性能、可用性、安全底线（按项目裁剪）
- **运行手册 / 部署说明**（Runbook / README ops 部分）
- **发布说明 / 变更日志**（Release notes / CHANGELOG）

---

## 怎么用才「不每次碰壁」

1. **按版本裁剪**：小工具可以「一页简报 + 半页领域表 + 接口草稿」；大系统再补全 C4、OpenAPI、完整用例。
2. **顺序可迭代**：允许先粗后细，但**每一轮迭代**都标明：当前版本覆盖了阶段 0～3 的哪几条产出物。
3. **概念模型是枢纽**：阶段 1 的词汇表和关系定下来后，阶段 2 的接口、阶段 3 的屏幕命名会省很多返工。
