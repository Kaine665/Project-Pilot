# 交付物类型契约文档

> **对应代码**: `src/types/deliverable.ts`
> **本文档定义了 Task Agent 中交付物（Deliverable）的类型体系，供 AI 推断和系统流转使用。**

## 定位

用户在项目跟踪链路中创建任务时，通常只写短语（如"开发者回复通知"），不会写明交付物。
AI 需要根据任务描述、所处环节、项目类型等信息，推断出这个任务完成后应该产出什么。

交付物类型的作用：
1. **Phase 1 推断** — AI 输出对任务的理解时，给出预期交付物组合
2. **Phase 3 计划** — 根据交付物类型决定执行步骤的构成
3. **Phase 5 验证** — 完成后检查实际产出是否覆盖了预期交付物

## 类型定义

一个任务通常产出**多个**交付物类型的组合。以下是全部 6 种类型：

### `ui` — 界面

用户可见的视觉产出。

- **产出物**: 新页面、新组件、弹窗、通知样式、图标、布局调整
- **信号词**: 页面、组件、按钮、弹窗、列表、面板、展示、显示、入口、界面、样式
- **典型场景**: "首页右上角反馈按钮"、"词汇量统计面板"、"复习卡片界面"
- **涉及文件**: `components/`, `screens/`, `pages/`, 样式文件

### `logic` — 逻辑

业务规则、算法、流程控制。不直接面向用户界面，也不直接操作数据库。

- **产出物**: 算法实现、状态机、触发规则、工具函数、hooks
- **信号词**: 算法、计算、触发、规则、通知（动作层面）、追踪、自动、流程、调度
- **典型场景**: "间隔重复算法"、"开发者回复时触发通知"、"阅读模式切换"
- **涉及文件**: `lib/`, `utils/`, `hooks/`, `services/`

### `data` — 数据

数据模型的变更，包括数据库 schema 和本地数据结构。

- **产出物**: 新表、新字段、migration、数据结构定义、Supabase RLS 策略
- **信号词**: 存储、记录、表、字段、数据、写入、schema、状态（持久化层面）
- **典型场景**: "写入 Supabase (user_id + category + content)"、"复习数据记录"
- **涉及文件**: `migrations/`, `schema/`, `types/`, 数据库配置

### `api` — 接口

系统边界上的通信端点。

- **产出物**: REST 端点、RPC 函数、webhook、Supabase Edge Function
- **信号词**: 接口、API、端点、请求、查询、上传、同步、服务端
- **典型场景**: "单词保存接口"、"截图/附件上传"、"反馈提交"
- **涉及文件**: `api/`, `routes/`, `functions/`, `services/`

### `infra` — 基建

不改变业务功能，改变系统运行方式。

- **产出物**: 环境变量、CI/CD 配置、部署脚本、监控告警、性能优化
- **信号词**: 部署、环境、配置、CI、性能、优化、迁移（系统层面）、分离
- **典型场景**: "dev/prod 环境分离"、"Supabase 自部署"、"划词响应速度优化"
- **涉及文件**: 配置文件、`.env`、`docker-compose`、CI 配置

### `analysis` — 分析

产出不是代码，而是信息和决策。

- **产出物**: 调研结论、方案文档、竞品分析、用户需求澄清、技术选型
- **信号词**: 了解、调研、分析、评估、对比、确认、了解、方案
- **典型场景**: "了解用户想要的上传格式"、"确认通知渠道方案"
- **涉及文件**: 通常不产出代码文件，产出在对话记录或文档中

## 推断规则

AI 按以下优先级推断交付物类型：

### 规则 1: 信号词匹配

扫描任务描述（task content）+ 环节描述（node description），匹配上述信号词。
命中多个类型时全部保留，因为一个任务通常是多类型组合。

### 规则 2: 环节上下文辅助

同环节的已完成任务（sibling tasks with status=done）暗示了当前任务的技术栈和模式。
例如：同环节已经有"文本输入框"（ui）和"写入 Supabase"（data + api），
那"截图/附件上传"大概率也是 ui + data + api 的组合。

### 规则 3: 项目类型约束

项目类型（`ProjectConfig.type`）会限制某些交付物的具体形态：

| 项目类型 | ui 的形态 | data 的形态 | api 的形态 |
|----------|-----------|-------------|-----------|
| react-native | RN 组件/Screen | Supabase/SQLite | Supabase RPC/Edge Function |
| nextjs | React 组件/Page | Prisma/文件存储 | API Route |
| node | CLI 输出/无 | 数据库/文件 | Express/Fastify 路由 |
| python | 无/Web 模板 | ORM/文件 | Flask/FastAPI 端点 |

### 规则 4: 无信号词时的默认推断

如果任务描述过于简短、无法匹配任何信号词：
- 优先标记为 `logic`（最通用的编程交付物）
- 加上 `confidence: 'low'` 标记，提示 Phase 2 需要追问

## 示例：完整推断过程

**任务**: "开发者回复通知"
**环节**: 提交后 — "提交后的跟进和闭环"
**项目**: ELApp (react-native)
**同环节已完成**: "查看历史反馈记录" ✅

推断过程：
1. "通知" → 命中 `logic`（触发规则）+ `ui`（通知展示）
2. "回复" 需要存储 → 命中 `data`（通知记录表）
3. 同环节有"查看历史反馈记录"已完成 → 说明反馈数据层已存在，通知可能复用
4. 项目类型 react-native → ui 是 RN 组件，data 是 Supabase

**推断结果**:
```
types: ['ui', 'logic', 'data']
confidence: 'high'
summary: "通知存储(data) + 回复触发通知(logic) + 用户端通知展示(ui)"
```
