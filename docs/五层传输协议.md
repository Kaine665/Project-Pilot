# 五层通信模型：从 TCP 到业务代码

> **定位**：非计算机网络权威分层模型（那是 OSI 七层 / TCP/IP 四层），而是从 ProjectPilot 实际架构出发，为了解释 **HTTP / API / SDK 三者关系**而提炼的实用分层。
>
> **诞生背景**：讨论 Agent 与 Todo 系统的交互方式时，发现 HTTP、WebSocket、SSE 属于一层，REST API、MCP Protocol 属于另一层，SDK 又属于另一层——但权威网络模型中它们全部被归入"应用层"，无法区分。因此向上拆细，形成五层。
>
> **last_reviewed**: 2026-04-08

---

## 五层总览

```
┌─────────────────────────────────────┐
│  ⑤ 应用层                           │  你的业务代码
│  dispatchTodoToAgent()              │
│  readTodosMerged()                  │
└──────────────┬──────────────────────┘
               │ 调用
┌──────────────▼──────────────────────┐
│  ④ 封装层（SDK）                     │  别人写好的代码库，装了就能用
│  Claude Agent SDK / Codex SDK       │
│  把下面几层包成 query() 等函数        │
└──────────────┬──────────────────────┘
               │ 遵循
┌──────────────▼──────────────────────┐
│  ③ 契约层（API / Protocol）          │  能调什么、参数是什么、返回什么
│  REST API、MCP Protocol             │
│  GraphQL、Function Calling Schema   │
└──────────────┬──────────────────────┘
               │ 承载于
┌──────────────▼──────────────────────┐
│  ② 传输层                           │  数据怎么从 A 送到 B
│  HTTP、WebSocket、SSE               │
│  gRPC、stdio 管道                   │
└──────────────┬──────────────────────┘
               │ 基于
┌──────────────▼──────────────────────┐
│  ① 网络层                           │  机器之间怎么连上
│  TCP/IP                             │
└─────────────────────────────────────┘
```

## 各层职责

| 层 | 名称 | 回答的问题 | 典型技术 |
|----|------|-----------|---------|
| ① | 网络层 | 两台机器怎么连上 | TCP/IP |
| ② | 传输层 | 数据怎么送过去、什么编码、单向还是双向 | HTTP、WebSocket、SSE、gRPC、stdio 管道 |
| ③ | 契约层 | 能调什么、怎么调、返回什么 | REST API、MCP Protocol、GraphQL、Function Calling Schema |
| ④ | 封装层 | 不想自己拼请求，给我一个函数直接调 | Claude Agent SDK、OpenAI Codex SDK、各种客户端库 |
| ⑤ | 应用层 | 用上面这些来实现具体业务 | ProjectPilot 的业务代码 |

## 各层详解

### ① 网络层

最底层。解决"两台机器怎么互相找到、怎么把字节送过去"。

对应 TCP/IP 协议栈。开发者几乎不直接操作这一层，操作系统和运行时已经处理好了。

### ② 传输层

在网络连通的基础上，定义**数据传递的模式**：

| 技术 | 方向 | 连接模式 | 典型场景 |
|------|------|---------|---------|
| **HTTP** | 请求-响应（单次） | 短连接 | REST API 调用 |
| **SSE** | 服务端→客户端（单向推送） | 长连接 | Agent 事件流推送 |
| **WebSocket** | 双向实时 | 长连接 | 聊天、协作编辑 |
| **gRPC** | 双向/流式 | 长连接（HTTP/2） | 后端微服务间通信 |
| **stdio 管道** | 双向 | 父子进程管道 | MCP 外部 Server（父进程通过 stdin/stdout 与子进程通信） |

**注意**：在权威的 OSI/TCP-IP 模型中，HTTP、WebSocket 等都归入"应用层"。本模型将其单独列为"传输层"，是为了和上面的契约层、封装层区分。

### ③ 契约层（API / Protocol）

定义**接口规范**——"你可以调什么、参数是什么格式、返回什么"。

这一层不包含实现代码，只是一份契约/合同。

| 技术 | 形式 | 特点 |
|------|------|------|
| **REST API** | URL + HTTP 方法 + JSON body | 最常见，简单直观 |
| **GraphQL** | 查询语言 + Schema | 客户端可以精确指定要什么数据 |
| **MCP Protocol** | JSON-RPC + Tool Schema | AI Agent 专用的工具扩展协议 |
| **Function Calling Schema** | JSON Schema（tool name + input_schema） | AI 模型 API 中定义可调用工具的规范 |

**契约层与传输层是正交的**——同一个契约可以跑在不同的传输上。例如 MCP Protocol 可以跑在 stdio 管道上，也可以跑在 HTTP+SSE 上。

### ④ 封装层（SDK）

把下面几层包装成**可直接调用的函数/类**。

没有 SDK 时，开发者需要自己拼 HTTP 请求、解析响应、处理错误重试、管理会话状态。有了 SDK，一个函数调用搞定：

```typescript
// 没有 SDK — 自己拼
const res = await fetch('https://api.anthropic.com/v1/messages', {
  method: 'POST',
  headers: { 'Authorization': 'Bearer sk-xxx', 'Content-Type': 'application/json' },
  body: JSON.stringify({ model: 'claude-sonnet-4-20250514', messages: [...] }),
});
const data = await res.json();
// 还要处理工具调用循环、流式输出、错误重试...

// 有 SDK — 一个函数
import { query } from '@anthropic-ai/claude-agent-sdk';
const result = query({ prompt: '...', options: { model: 'claude-sonnet-4-20250514' } });
```

SDK 内部封装了：传输层通信 + 契约层协议遵循 + 错误处理 + 状态管理。

### ⑤ 应用层

最顶层。调用 SDK（或直接调用更低层）来实现具体业务逻辑。

ProjectPilot 中的 `agentChatManager.start()`、`dispatchTodoToAgent()`、`readTodosMerged()` 等都属于这一层。

## ProjectPilot 实例

### 前端读取 Todo 列表

```
⑤ 应用层：    fetch('/api/todos')
④ 封装层：    （无，前端直接用浏览器内置 fetch）
③ 契约层：    REST API — GET /api/todos → { todos: [...] }
② 传输层：    HTTP
① 网络层：    TCP → localhost
```

### Agent 会话事件推送到前端

```
⑤ 应用层：    streamSSE() 推送 AgentEvent
④ 封装层：    hono/streaming
③ 契约层：    自定义事件格式 { type: 'text_delta', text: '...' }
② 传输层：    SSE（Server-Sent Events）
① 网络层：    TCP → HTTP 长连接
```

### Agent 调用 Claude API（通过 SDK）

```
⑤ 应用层：    agentChatManager.start()
④ 封装层：    Claude Agent SDK — query()
③ 契约层：    Anthropic Messages API — POST /v1/messages
② 传输层：    HTTP（流式）
① 网络层：    TCP → api.anthropic.com
```

### Agent 调用外部 MCP 工具

```
⑤ 应用层：    AI 决定调 mcp__github__create_issue
④ 封装层：    SDK 内部的 MCP 客户端
③ 契约层：    MCP Protocol（JSON-RPC）
② 传输层：    stdio 管道
① 网络层：    （无，进程间通信）
```

### Agent 调用内存 MCP 工具（Function Calling）

```
⑤ 应用层：    AI 决定调 mcp__todo__update_todo
④ 封装层：    SDK — createSdkMcpServer()
③ 契约层：    MCP Protocol（形式上遵循接口规范）
② 传输层：    （无，同进程函数调用）
① 网络层：    （无）
```

> 内存 MCP 在契约层遵循 MCP 接口规范，但传输层和网络层被完全跳过——数据不离开进程。这是它既可靠又高效的原因。

## 与权威模型的关系

| 本模型 | OSI 七层 | TCP/IP 四层 |
|--------|---------|------------|
| ① 网络层 | 3 网络层 + 4 传输层 | 2 网络层 + 3 传输层 |
| ② 传输层 | 7 应用层（部分） | 4 应用层（部分） |
| ③ 契约层 | 7 应用层（部分） | 4 应用层（部分） |
| ④ 封装层 | 不存在 | 不存在 |
| ⑤ 应用层 | 不存在（超出模型范围） | 不存在（超出模型范围） |

权威模型关注的是"网络通信"，在 HTTP 之上就不再细分。本模型关注的是"一个 AI Agent 系统的完整调用栈"，因此在 HTTP 之上继续拆分了契约层、封装层、应用层。

**本模型不替代权威模型，而是在权威模型的顶层之上，针对 AI Agent 应用场景做了进一步细分。**

## 术语速查

| 术语 | 属于哪层 | 一句话解释 |
|------|---------|-----------|
| TCP/IP | ① 网络层 | 机器间通信的基础协议 |
| HTTP | ② 传输层 | 请求-响应模式的数据传输协议 |
| WebSocket | ② 传输层 | 双向实时数据传输协议 |
| SSE | ② 传输层 | 服务端向客户端单向推送的协议 |
| gRPC | ② 传输层 | Google 的高性能远程调用框架（基于 HTTP/2 + Protocol Buffers） |
| stdio 管道 | ② 传输层 | 父子进程间通过标准输入/输出通信 |
| REST API | ③ 契约层 | 基于 HTTP 的接口设计规范（URL + 方法 + JSON） |
| MCP Protocol | ③ 契约层 | AI Agent 工具扩展的标准协议 |
| GraphQL | ③ 契约层 | 客户端可精确查询的 API 规范 |
| Function Calling | ③ 契约层 | AI 模型调用外部工具的接口规范（tool name + JSON Schema） |
| SDK | ④ 封装层 | 封装好的代码库，装了直接调函数 |
| 业务代码 | ⑤ 应用层 | 你写的 ProjectPilot 逻辑 |
