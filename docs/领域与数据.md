## 0. 通用语言：会话（连续上下文）与实现映射

**领域用语「会话」**：指用户与某个 **Agent** 的一次 **连续上下文**——同一条对话线程、同一套消息历史与会话级配置；可挂 `projectKey`、可归档，生命周期独立于 Agent 模板。

| 说法 | 含义 |
|------|------|
| **会话**（建模 / 口头） | 上表所述连续上下文 |
| **`AgentChatSession`**（`src/types/agent-chat.ts`） | 含 `messages` 的完整会话对象（内存/API 常用） |
| **`SessionMeta`** | 索引中的会话元数据（**不含** `messages`）；磁盘为 `sessions/index.json` 中的数组元素 |
| **`AgentChatSessionsData`** | `{ sessions: SessionMeta[] }`，索引文件整体形状 |
| **消息正文** | `sessions/messages/<sessionId>.jsonl`（与索引分离） |
| **「Agent Chat」** | 产品/模块名（路由、目录 `agent-chat`），**不是**与「会话」并列的第二类实体；实现上即「会话」的载体 |

**历史类型 `LegacyTaskWorkerSession`**（`types/index.ts`）：旧 Task Worker 数据形状，**不是**当前 Agent Chat 的持久化模型；仅保留类型以兼容旧文档/工具叙述。详见 **[`docs/data-storage.md`](data-storage.md)** 与 **`MEMORY.md`**。

## 1. 五个关注面

领域分为五组关注面，彼此交叉但各有主题：

### 核心循环

五关注面不是并列的五块，而是一条流水线上的五段：

```
触发（③）→ 寻址（①）→ 给料（④）→ 执行记录（②）→ 结果追踪（⑤）
```

| 环节 | 对应关注面 | 系统在做什么 |
|------|-----------|-------------|
| 有件事来了 | **③ Trigger** | 把各种来源（人/定时/事件）统一成一条消息 |
| 该谁做、在哪做 | **① Scope** | 定位 Project → Agent → Session |
| 带着什么去做 | **④ Resource** | 把指令、知识、工具拼到上下文里 |
| 做的过程 | **② Execution** | 每一步留痕（Event），有目标的尝试标为 Run |
| 做完了怎么样 | **⑤ Tracking** | 这件事完成了吗、进度如何 |

Scope（①）贯穿全程——每一步都要用它来确定「我在哪、我能看到什么」。

下表列出五关注面的具体概念：

| # | 关注面 | 包含的核心概念 | 回答的问题 |
|---|--------|---------------|-----------|
| ① | **Scope（身份与可见性）** | Global、Project、Agent、Session | 东西放在哪一级？谁能看到？ |
| ② | **Execution（执行模型）** | Event、Step、Run、Goal、Evaluation | Session 里 AI 具体做了什么？做得怎么样？ |
| ③ | **Trigger（触发机制）** | Trigger（条件类型：manual / cron / event） | 什么时候戳一下？ |
| ④ | **Resource（上下文来源）** | 开放集合（当前：Document、Skill、MCP 等） | Agent 可用的资源，类型可扩展 |
| ⑤ | **Tracking（任务与进度）** | Task | 项目里有哪些事要做？做到哪了？ |

**交叉规则**：
- ① Scope 是贯穿一切的"地址系统"，② ③ ④ ⑤ 的实体都要挂在某个 scope 上。
- ④ Resource 可出现在任何 scope 级别。
- ③ Trigger 也有 scope（project 级、agent 级等）。
- ③ Trigger 触发后给 Session 发消息，由 Agent 决定是否开 Run，最终落入 ② Execution。
- ⑤ Task 属于 Project 级，可关联到具体的 Session/Run（实际执行时）。

## 2. ① Scope：包含关系

```
Global ⊃ Project ⊃ Agent ⊃ Session
```

- **包含关系，不是正交维度**。简洁优先。
- **可见性规则：向上继承，向下隔离**。Session 能看到它所属 Agent 的、Agent 所属 Project 的、以及 Global 的资源。反过来不行。
- 存在"全局 Agent"（不绑定任何 Project）等边界情况，但整体仍遵循包含关系。

### 各级定义

| 概念 | 含义 |
|------|------|
| **Global** | 系统级，所有 Project 共享的空间。全局指令（`prompts/global.md`）对所有会话生效 |
| **Project** | 用户注册的一个代码仓库/工作区。业务键为 `projectKey`。可配项目级指令（`prompts/projects/<key>.md`） |
| **Agent** | 可配置的 AI 执行单元：模型/供应商、能力开关、执行模式等。主系统指令外置为 `prompts/agents/<id>.md`，resolve 优先级：用户文件 → 内置默认 → 内联 |
| **Session** | 用户与某个 Agent 的一次连续上下文。可聊多个话题、做多件事、搁置产生 Task 等。可有会话级指令覆盖（`prompts/runtime/`），仅本次生效 |

## 3. ② Execution：Session 内部的执行模型

### 核心原则

- **Event 流是主角**。Session 拥有一条完整的、连续的 Event 时间线。
- **Run 是标记区间**，不是容器。Run 在 Event 流上"画一个框"，标注 Goal 和 Evaluation。
- 不在任何 Run 里的 Event 正常存在——自由对话、探索是 Session 的常态，Run 是特殊情况。

### 层次（三层）

```
Session（连续上下文）
│
├── Event 时间线（所有原子动作的完整记录）
│    ├── Event #1: message
│    ├── Event #2: thinking
│    ├── ...
│    ├── Event #15 ─┐
│    ├── ...        │ ← Run #1 标记的区间
│    ├── Event #42 ─┘
│    ├── Event #43: message  ← 自由对话，不属于任何 Run
│    └── ...
│
└── Run 列表（标记在 Event 流上的区间）
     └── Run #1
          ├── Goal: "修复登录 bug"
          ├── Step 1（AI 自主声明的逻辑步骤）
          │    ├── Event #15: thinking
          │    ├── Event #16: tool_use (grep)
          │    └── Event #17: message
          ├── Step 2
          │    ├── Event #18: tool_use (edit file)
          │    └── Event #19: artifact_create
          └── Evaluation: "没修好，根因判断错误"
```

### 各级定义

| 概念 | 语义 | 边界由谁决定 |
|------|------|-------------|
| **Event** | 原子动作：一次有意义的、可独立理解的动作 | 系统自动记录 |
| **Step** | Run 内的逻辑步骤，把多个 Event 组成"做了一件事" | **AI 自主声明**（系统提供机制，AI 决定划分） |
| **Run** | 一次目标导向的尝试 | AI 或用户发起 |
| **Goal** | Run 的目标——这次尝试想做什么 | Run 创建时设定 |
| **Evaluation** | Run 的结果判定 | Run 结束时产生 |

### 术语映射（领域 ↔ 代码）

| 领域术语 | 代码 / 实现 | 说明 |
|---------|------------|------|
| Turn（回合） | `AgentChatRun`（`agent-chat-manager.ts`） | 一次 user → assistant 的完整回合；代码命名历史沿用 |
| Event（执行事件） | `ExecutionEvent`（`types/execution.ts`） | Turn 结束后归约出的完整事件，落盘到 `sessions/events/<sessionId>.jsonl` |
| Run（执行尝试） | `ExecutionRun`（`types/execution.ts`） | 跨多个 Turn 的目标导向尝试，落盘到 `sessions/runs/<sessionId>.json` |
| 流式 delta | `AgentEvent`（`types/index.ts`） | 推给前端的细粒度事件（text_delta、tool_use_start…），**不落盘** |
| 对话记录 | `ChatMessage`（`types/agent-chat.ts`） | 落盘到 `sessions/messages/<sessionId>.jsonl`，前端聊天视图依赖 |
| 上轮摘要 | `SessionExecution`（`chat-managers/types.ts`） | 存在 `sessions/index.json` 中的 meta 上 |

### 为什么需要三层而不是两层

> Run 是"尝试"，Step 是"步骤"。就算只做了一步，也是一次尝试。
> 这两个概念必须分开：Run 承载"试了几次、每次判断如何"的语义，Step 承载"具体做了什么"的语义。

### Event 类型（已实现）

| Event 类型 | 含义 |
|-----------|------|
| `turn_start` | 一次回合开始 |
| `user_message` | 用户发送的消息 |
| `thinking` | AI 的推理/思考过程（完整文本，非 delta） |
| `tool_call` | 调用工具（完整：name + input + output + status） |
| `assistant_message` | AI 回复（完整文本 + contentBlocks） |
| `turn_end` | 回合结束（status、tokenUsage） |
| `run_open` | 开启一次 Run（goal、taskId） |
| `run_close` | 关闭一次 Run（outcome、evaluation） |
| `error` | 出错 |

**关键设计**：Event 是 Turn 结束时从内存累积归约出的**完整事件**，不是流式 delta。delta（`text_delta`、`thinking_delta`）是传输层概念，不落盘。

### Evaluation 结果

| outcome | 含义 |
|---------|------|
| `success` | 目标达成 |
| `failure` | 目标未达成 |
| `partial` | 部分完成 |
| `shelved` | 搁置，暂不继续 |

可附带自由文字说明。

### 实现阶段

| 阶段 | 内容 | 状态 |
|------|------|------|
| **第一期** | Event 落盘（`ExecutionEvent` + JSONL 存储 + API） | ✅ 已实现 |
| **第二期** | Run 生命周期（`ExecutionRun` + 开/关 API + 前端） | ✅ 后端已实现，前端待建 |
| **第三期** | Step 声明机制（AI 自主声明逻辑步骤） | 暂缓——依赖模型配合，等 Run 稳定后建设 |

## 4. ③ Trigger：触发机制

### 核心定义

Trigger 是一种统一的触发机制，**只负责"戳一下"（给 Session 发消息），不负责决定怎么做**。决策权在 Agent。

三种条件类型本质相同（条件 + 动作），区别仅在条件：

| 条件类型 | 触发条件 | 举例 |
|----------|---------|------|
| **manual** | 人或 Agent 主动触发 | 用户点"开始"、Agent 委派另一个 Agent |
| **cron** | 时间到了 | `*/5 * * * *` 每 5 分钟 |
| **event** | 外部事件匹配 | GitHub PR opened + base=main |

### Trigger 结构

```
Trigger
 ├── condition:
 │    ├── type: "manual" | "cron" | "event"
 │    └── config: (cron 表达式 / 事件匹配规则 / 无)
 ├── sessionMode: "continue" | "new"
 ├── targetAgent: 要执行的 Agent
 ├── scope: 挂在哪一级（project / agent）
 ├── sourceSessionId?: 产生此 Trigger 的原始 Session（来源链接）
 ├── status: pending | active | done | disabled
 └── ...各条件类型特有配置
```

### 关键决策

- **谁能创建**：人和 Agent 都能创建 Trigger。
- **生命周期**：manual 类触发后变 done（保留记录，不删除）；cron 持续执行直到 disabled；event 持续监听直到 disabled。
- **触发后的行为**：给 Session 发一条带上下文的消息（作为 Event 进入 Event 流），Agent 自己判断是否需要开 Run。
- **Session 策略**：`sessionMode` 决定续接还是新建。同 Agent 周期性任务通常续接；跨 Agent 委派必须新建。

### 与旧概念"Todo"的关系

> 旧的"Todo"概念实际混合了两件事：触发机制（"现在去做"）和任务跟踪（"有哪些事、做到哪了"）。
> 现在拆为：**Trigger**（条件类型 manual）负责触发，**Task**（⑤ Tracking）负责跟踪。

## 5. ④ Resource：上下文来源

### 定位

**Resource 是 AI 上下文的来源，类型是开放集合。**

每种来源类型有自己的结构规范和管理方式，通过统一的注入机制（ResourceRef + Loader）参与上下文组装。当前已有：

| 来源类型 | 说明 |
|---------|------|
| **Document** | 知识性内容，有索引和生命周期 |
| **Skill** | 遵循业界结构规范的能力包 |
| **MCP** | 遵循 MCP 协议的工具服务，有运行时调用能力 |

将来可接入新的来源类型（SOUL、Workflow 等），不改变整体机制。

**Scope 级指令**（global / project / agent / session 的提示词源文件）不单列资源类型，归入 §2 各 scope 定义中。

**完整上下文的组装策略**（注入位置、优先级、截断等）属于架构/实现层，不在领域模型中规定。

### Artifact 不是独立实体

Artifact（产出物）不是一个需要单独管理生命周期的实体类型，而是**Event 流上的一个视角**：

- 从 Event 流中筛选出产出相关的 Event（如 `artifact_*`、某些 `tool_use`），即可得到 Session 的全部产出
- 产出的形态可以是 Document、Skill、代码文件、指令/提示词内容变更等——**Artifact 描述的是来源/角色（"这是产出的"），不是内容形态**
- 不需要独立建模，Event 自身的结构化字段足以承载产出信息

> 参考：Poco 也没有独立的 Artifact 数据实体，其"Artifacts view"是前端从工具执行记录中提取产出物进行渲染。

### 关键特性

- **跨 scope**：Resource 可出现在 Global、Project、Agent、Session 任何一级
- **双重角色**：同一个 Document 可以是预加载的输入，也可以是 Session 里产出后留存的

## 6. ⑤ Tracking：任务与进度

**状态：初步定义，尚未深入讨论。**

### 核心定义

Task 是 **Project 级别的跟踪实体**——"这个项目有哪些事情要做，做到哪了"。

```
Task
 ├── 属于某个 Project（scope = Project）
 ├── 描述：要做什么
 ├── status: pending → doing → done
 ├── 进度信息
 └── 可选：关联的 Session / Run（实际执行时）
```

### 与 Trigger 的关系

Task 和 Trigger 是两个独立概念：
- **Task = "做什么 + 做到哪了"**（跟踪）
- **Trigger = "什么时候戳一下"**（触发）

一个 Task 可以被 manual Trigger 启动执行，也可以不经 Trigger、在 Session 中直接做。

### 并行执行看板与用户待办（实现侧对齐）

- **用户待办（Todo）**：磁盘上主要为 `todos.json` / `todos/entries/`，面向「计划里有哪些事、状态如何」。
- **并行执行看板**：对应 `agents/active-tasks.json`，登记**当前**各 Agent **正在执行的**并行任务，供其他 Agent 读表感知范围、减少踩脚；不是用户的待办清单。二者可通过 `todoId` / `activeTaskId` 可选关联，但语义仍应区分。

- Task 的完整字段与生命周期

## 7. 设计原则备忘

- **先定语义，后做基础设施**。领域模型关注的是概念和关系，不是队列调度、分布式锁等执行细节。
- **Event 流是第一公民**。Run、Step、Artifact 都是 Event 流之上的视角/标注，不是独立的容器。
- **Scope 是包含关系**。Global ⊃ Project ⊃ Agent ⊃ Session，向上继承、向下隔离。
- **Resource 类型是开放集合**，各遵循自己的结构规范；scope 级指令归入各 scope 定义，不单列资源类型；上下文组装策略属于实现层。
- **Trigger 只负责"戳一下"**。触发后发消息，Agent 自己决定怎么做。
- **Task 与 Trigger 分离**。跟踪是跟踪，触发是触发。
