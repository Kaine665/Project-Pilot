# 内部架构

ProjectPilot 应该围绕“项目上下文的生命周期”来设计，而不是围绕一组功能列表来设计。

## 分层结构

```text
1. Context Store：上下文存储层
2. Context Model：上下文模型层
3. Context Index：上下文索引层
4. Context Pack Builder：上下文打包层
5. Integration Layer：集成层
6. Review Console：审核控制台
```

## 1. Context Store：上下文存储层

存储层负责让项目上下文本地优先、可检查、可备份、可导出、可恢复。

早期可以使用本地文件或 SQLite。关键不是数据库技术本身，而是用户能看见和控制自己的项目记忆。

## 2. Context Model：上下文模型层

核心对象：

- `Project`：正在被推进的项目。
- `Memory`：稳定的项目事实和背景。
- `Decision`：选择、原因、替代方案和时间。
- `Task`：待办、进行中或已完成的工作。
- `Constraint`：规则、限制、偏好和已知风险。
- `Artifact`：文档、链接、文件、代码区域或外部参考。
- `Run`：一次 AI 工具执行记录。
- `ContextPack`：AI 工具开工前收到的上下文包。
- `MemoryPatch`：AI 工具收工后提出的项目记忆更新。

其中最重要的两个对象是 `ContextPack` 和 `MemoryPatch`。

## 3. Context Index：上下文索引层

索引层负责为某个任务找到合适的上下文。

早期索引可以很简单：

- 关键词搜索
- 类型过滤
- 最近活跃
- 人工固定
- 项目标签

Embedding、关系图等高级能力可以在核心闭环跑通之后再引入。

## 4. Context Pack Builder：上下文打包层

这是 ProjectPilot 最核心的生产能力。

它把已保存的项目信息转换成一份适合 AI 工具读取的上下文包。

一份好的 `ContextPack` 应该包含：

- 项目摘要
- 当前任务意图
- 相关事实
- 相关决策
- 当前约束
- 当前任务状态
- 相关文档和代码区域
- AI 工具执行结束后应该回报什么

## 5. Integration Layer：集成层

最优先的集成路径是 MCP。

后续可以扩展：

- CLI
- 本地 HTTP API
- 文件协议
- Git hooks
- IDE 插件
- 云同步或 webhook

MCP 应该排在第一位，因为外部 AI harness 可以把它当作工具层调用。

## 6. Review Console：审核控制台

审核控制台的存在，是为了防止项目记忆变成黑盒。

用户的核心动作是：

- 审核待写入的记忆更新
- 接受、修改、拒绝、合并、固定或归档记忆
- 查看生成过的上下文包
- 查看 AI 工具执行记录
- 修正过时或错误的项目上下文
- 管理任务、决策和约束

UI 应该是上下文控制台，而不是聊天优先的产品。
