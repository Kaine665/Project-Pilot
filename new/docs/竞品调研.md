# 竞品调研

调研时间：2026-04-24

## 调研目标

本次只看和新定位接近的产品：

> ProjectPilot 是本地优先的项目上下文服务器，通过 MCP 被 Claude Code、Cursor、Codex 等 AI harness 调用，负责项目上下文的读取、写回、审核和复用。

因此不把普通 agent 平台、普通任务管理工具、普通知识库、普通 IDE 插件列为直接竞品，除非它们明确处理“AI 工具跨会话项目上下文”问题。

## 初步结论

这个方向已经有明显竞品，而且数量不少。

最拥挤的区域是：

- MCP 持久记忆
- Claude Code 项目记忆
- 任务 + 决策 + 会话交接
- 代码库上下文检索
- 上下文压缩与跨会话恢复

但大多数竞品更像“记忆 MCP”或“任务记忆 MCP”，还没有明显形成“项目上下文服务器 + 人类审核控制台 + ContextPack / MemoryPatch 生命周期”这个完整产品形态。

ProjectPilot 的机会不在“也有 memory tool”，而在把项目信息生命周期做清楚：

```text
开工前：生成 ContextPack
执行中：记录 Run
收工后：生成 MemoryPatch
人审核：接受 / 修改 / 拒绝
下次：复用经过审核的项目上下文
```

## GitHub / MCP 生态竞品

### 1. Agentic Tools MCP

地址：https://github.com/Pimzino/agentic-tools-mcp

定位：MCP server，提供任务管理和 agent memory，并支持 project-specific storage。

接近点：

- 项目级隔离
- 任务管理
- agent memory
- VS Code GUI + MCP server 组合

和 ProjectPilot 的差异：

- 更偏“任务管理 + 记忆工具生态”。
- ProjectPilot 应该更强调 ContextPack / MemoryPatch，也就是 AI 工具开工前和收工后的项目信息流。

### 2. Context Engineering MCP

地址：https://github.com/bralca/context-engineering-mcp

定位：给 Cursor、Claude Code、VS Code 使用的 MCP server，让 AI agent 理解代码库、架构和开发模式，减少 context loss。

接近点：

- 明确解决 context loss。
- 面向复杂软件项目。
- 兼容 Cursor、Claude Code、VS Code。
- 包含代码库分析、架构模式识别、feature planning。

和 ProjectPilot 的差异：

- 更偏 codebase understanding 和 feature planning。
- ProjectPilot 应该覆盖更完整的项目上下文，包括决策、任务、约束、文档、执行记录和人类审核。

### 3. Kratos MCP

地址：https://github.com/ceorkm/kratos-mcp

定位：给 AI coding tools 的 memory system，强调“Never explain your codebase again”和项目隔离。

接近点：

- 和 ProjectPilot 的痛点高度接近。
- 强调 coding tool 的项目记忆。
- MCP server 形态。

和 ProjectPilot 的差异：

- 更像代码项目记忆系统。
- ProjectPilot 应该把“上下文回写审核”和“上下文包生成质量”作为核心差异，而不是只做记忆存取。

### 4. MCP Memory Keeper

地址：https://github.com/mkreyman/mcp-memory-keeper

定位：Claude Code 的持久上下文管理 MCP server，用于保存工作历史、决策和进展，避免 compaction 或新会话导致上下文丢失。

接近点：

- 明确保存 work history、decisions、progress。
- 支持 checkpoint。
- 支持不同 Claude 会话共享上下文。
- 很贴近“会话交接”问题。

和 ProjectPilot 的差异：

- 更像上下文保存与恢复工具。
- ProjectPilot 应该把“项目上下文对象模型”和“审核控制台”做成一等公民。

### 5. MemoryGraph

地址：https://github.com/memory-graph/memory-graph

定位：面向 coding agents 的图数据库 MCP memory server，用关系跟踪保存和检索跨会话知识。

接近点：

- 持久记忆。
- 关系图。
- 支持 Claude Code。
- 强调 coding agent。

和 ProjectPilot 的差异：

- 更偏 memory backend / graph retrieval。
- ProjectPilot 应该更偏产品化的项目上下文生命周期，而不只是底层 memory graph。

### 6. MCP Memory Service

地址：https://github.com/doobidoo/mcp-memory-service

定位：AI agent pipeline 的 persistent shared memory backend，支持 LangGraph、CrewAI、AutoGen、Claude 等，包含 REST API、知识图谱、自动 consolidation。

接近点：

- 共享记忆后端。
- agent 之间共享决策和知识图谱。
- 支持 self-hosted / cloud-hosted。
- 支持 Remote MCP。

和 ProjectPilot 的差异：

- 更偏通用 agent memory backend。
- ProjectPilot 更应聚焦“项目上下文服务器”，尤其是人类可审计的项目事实、任务、决策和执行闭环。

### 7. MCP Local Memory

地址：https://github.com/Beledarian/mcp-local-memory

定位：本地 memory server，支持文本、实体、关系、任务，并通过 MCP Resources 暴露 current context / turn context。

接近点：

- 本地优先。
- 有 current context / turn context 资源。
- 支持任务和上下文提炼。

和 ProjectPilot 的差异：

- 更偏通用本地记忆。
- ProjectPilot 应该更强调“项目级上下文包”和“收工后的记忆补丁审核”。

### 8. MCP Task Orchestrator

地址：https://github.com/EchoingVesper/mcp-task-orchestrator

定位：MCP task orchestration server，自动记录决策、实现和测试，提供任务编排、专家角色和持久记忆。

接近点：

- 任务编排。
- 自动记录决策、实现和测试。
- 持久记忆。
- 支持 Claude Desktop、Cursor、Windsurf、VS Code。

和 ProjectPilot 的差异：

- 更偏“AI 辅助开发流程编排”。
- ProjectPilot 不应该先和执行编排抢位置，而应先做外部 harness 可调用的项目上下文层。

### 9. mindpm

资料页：https://openclawradar.com/article/mindpm-free-mcp-server-persistent-project-memory-claude

定位：基于本地 SQLite 的 Claude 持久项目记忆 MCP server，跟踪任务、决策、笔记和会话。

接近点：

- 本地 SQLite。
- 任务、决策、笔记、会话。
- 内置 Kanban UI。
- 目标就是解决每次 Claude Code 开始都要重新解释项目的问题。

和 ProjectPilot 的差异：

- 这是非常接近的竞品。
- ProjectPilot 必须在 ContextPack / MemoryPatch、人类审核、跨 harness 接入、项目上下文质量控制上做得更系统。

### 10. Claude Code Buddy

资料页：https://mcpmarket.com/server/claude-code-buddy

定位：通过 MCP 增强 Claude Code，提供 project memory、task routing、expert responses 和模型选择。

接近点：

- 明确坐在 Claude Code 和用户之间。
- 提供 project memory。
- 有任务路由和专家 agent。

和 ProjectPilot 的差异：

- 更像 Claude Code 增强器。
- ProjectPilot 应保持 harness 中立，成为 Claude Code、Cursor、Codex 等都能调用的项目上下文服务器。

## X / 社区讨论信号

X 上公开结果更多是方法论，不一定是产品竞品。

主要信号：

- 很多人已经把 `CLAUDE.md` 视作 project memory。
- 社区在讨论 Claude Code 的结构化项目方式：`CLAUDE.md`、skills、hooks、MCP、agents。
- 有人明确提到“项目越大，Claude Code 不能只当聊天窗口，需要 separation of concerns”。
- 有人提到 Claude 产品里的 per-project memory 和 explorer view 是关键，但还缺 project-scoped skills、MCPs、sub-agents。

判断：

这说明市场教育正在发生。用户已经感受到“项目记忆”和“项目级上下文”问题，但很多解决方案还停留在文件约定、配置技巧和零散 MCP 工具。

ProjectPilot 可以把这些散乱实践产品化。

## 小红书公开搜索结果

公开搜索没有明显发现“项目上下文服务器 / AI 项目记忆 MCP”同定位产品讨论。

搜索结果主要集中在另一类 MCP：

- 小红书平台自动化 MCP
- 内容发布、搜索、账号登录、运营自动化
- xiaohongshu-mcp / xhs-toolkit 等

这些不是 ProjectPilot 的直接竞品，因为它们是“给 AI 操作小红书平台”的垂直工具 MCP，不是“给 AI 工具提供项目上下文”的项目信息 MCP。

但它们有一个启发：

MCP 在中文社区的认知更容易从“能让 AI 操作某个系统”开始。ProjectPilot 对中文用户解释时，可以说：

> 小红书 MCP 让 AI 操作小红书；ProjectPilot MCP 让 AI 读取和更新你的项目上下文。

### 直接竞品

最接近：

- Claude Code Buddy

### 间接竞品

- MemoryGraph

- `CLAUDE.md`

- Notion / Obsidian / Linear + prompt 手动粘贴

## 对 ProjectPilot 的启发

### 不能只说“持久记忆”

这个词已经很拥挤。

ProjectPilot 应该避免落入“又一个 memory MCP”的位置。

### 要强调项目信息生命周期

核心对象应该是：

- `ContextPack`：AI 开工前收到什么。
- `Run`：AI 执行中发生什么。
- `MemoryPatch`：AI 收工后建议项目记住什么。
- `Review`：用户如何审核这些更新。

### 要强调人类审核

很多 memory MCP 会让 AI 直接记忆。ProjectPilot 应该把可见、可改、可拒绝作为核心信任机制。

### 要保持 harness 中立

不要只做 Claude Code 插件。

更好的位置是：

```text
Claude Code / Cursor / Codex / OpenClaw / 其他 MCP client
        |
        v
ProjectPilot Context Server
```

### 要做上下文质量，而不是存储容量

差异不在“我能存更多记忆”，而在：

- 给 AI 的上下文是否刚好够用。
- 重要决策是否能被正确召回。
- 过期信息是否能被发现。
- 用户是否能信任写回结果。

## 暂定产品差异化句子

ProjectPilot 不是又一个 memory MCP。

ProjectPilot 是项目上下文服务器：它为 AI 工具生成可执行的 ContextPack，并把执行后的结果转成可审核的 MemoryPatch，让项目上下文在多次 AI 工作之间持续变好。
