是，当前架构对 sub agent 的支持“能用”，但还不算“架构上支持得好”。更准确地说，它现在是原型可用级，不是稳定基础设施级。

核心问题不是“不能调”，而是这套链路有几个结构性短板：

状态分裂。运行态在内存里的 agentChatManager.runs，历史态在磁盘 agent-chat-sessions.json，而 call-agent / call-agent-batch 要同时读 /status 和 /sessions/[id] 才能拼出结果。这就是我们刚才碰到竞态误判的根因。见 agent-chat-manager.ts 和 call-agent-batch.ts。
完成语义不稳。内存状态先变 completed，持久化稍后才落盘，导致轮询方看到“已完成但还没结果”的窗口。这种语义对编排层很危险。
结果通道太弱。现在 sub agent 的标准产物基本只有一段 assistant 文本，缺少结构化结果、标准错误码、artifact 引用、明确的完成/失败原因。
批量调用还是外置 CLI 轮询，不是系统内的一等公民。call-agent-batch 本质上是客户端脚本，不是服务端任务编排器。
取消、重试、超时、递归保护都不够硬。尤其 depth 还是调用方自觉传，不是系统强约束。见 call-agent.ts。
parentSessionId 目前更多是“挂关系”，不是完整的父子任务模型。能查 children，但没有真正的汇总状态、子任务树、失败传播、依赖控制。

但也不能说它架构完全不行，它已经有几块是对的：

子会话持久化是有的
parentSessionId 链路是通的
API、CLI、会话存储三层已经打通
批量并发的雏形已经存在

所以结论是：

如果目标是“偶尔调两个 sub agent 做实验”，现在够用
如果目标是“把 sub agent 当稳定编排基础设施”，现在还不够好

我建议后续演进方向分三步：

先统一状态源
把“运行状态”和“最终结果”变成一个正式的任务记录，不要再让 CLI 自己拼 /status 和 /session。

再做结构化结果协议
sub agent 返回 { status, summary, output, artifacts, error }，而不是只靠自然语言文本判断。

最后再上真正编排
把批量、超时、取消、重试、依赖、父子聚合放进服务端 manager，而不是放在 CLI 里轮询。
